## 3. 目标边界

### 3.1 仓库与构建

- 保留产品仓库和一个 zju-connect fork；产品专用组件继续在产品仓库维护。
- 补丁归并后，产品的 `third_party/zju-connect` 改为指向该 fork 的固定子模块提交；Hub 和 Worker 都从这一份源码构建。
- 兄弟 `zju-connect/` 可作为显式开发覆盖。正式构建拒绝未声明的覆盖、漂移的引用和脏内核状态。
- 正式构建明确每个模块的 `GOWORK`、依赖替换、工具链和组件集合。P0 先固定现有双来源，P4 再切换到单一来源。
- 保留产品主模块；现有 e2e 模块按实际用途维护，不为每个功能新建 Go 模块或仓库。

### 3.2 运行时与依赖

| 部分 | 目标职责 | 生命周期 |
|---|---|---|
| Hub | GUI、用户配置、会话编排、路由与组件状态 | 主程序运行期间 |
| VPN Worker | 现有 EasyConnect 协议会话 | 按现有会话管理；本轮先保留入口位置 |
| 网络助手 | 特权网络操作、所有权和故障恢复 | 沿用平台现有模型，不强行统一为普通子进程 |
| Cleanup | 扫描、备份、清理、恢复 | 按任务启动，任务结束退出 |
| Relay | 分享服务、发现、导入分享的连接运行时 | 存在有效任务时运行，无任务时完整停止 |

```text
Hub 页面 → 轻量 client / contract → 本机 IPC → 对应 service
                        ↑
               components 管理进程生命周期

基础 VPN 会话 ← 可选适配器 → relay 能力
```

约束：

1. GUI 不导入可选组件的 `service`；基础 `vpn` 不依赖 relay 的服务实现。
2. 在装配层显式注入可选连接器；未知或未安装的协议返回明确错误，不退回 aTrust 登录或直接联网。
3. 构造函数只准备轻量对象；启用操作创建运行资源；停止操作取消任务、关闭句柄、等待退出、解除引用。
4. “从未启用”场景不启动功能专用循环、监听、扫描或大缓存。既有用户明确启用的自动恢复意图仍需生效。
5. 页面关闭与业务停止分开：关闭分享页面不停止有效分享或导入连接；关闭发现只撤销发现任务。
6. Hub 负责共享用户配置的写入。组件通过事件报告结果；组件恢复日志单独保存并有明确所有权。
7. UI 消费有界状态快照，在 UI 线程应用；不在每次绘制时执行 IPC 或扫描。旧实例、旧代次的事件不得覆盖新状态。
8. 进程分离用于隔离资源和生命周期，不预设启用时总内存更低；比较完整进程树。
9. 停止时保留必要恢复日志和内网归属保护，不以降低占用为由删除这些状态。

## 4. 分阶段执行计划

执行顺序为 P0 → P1 → P2 → P3 → P4 → P5 → P6。每阶段验收后再进入下一阶段，不同时展开大范围目录迁移和协议行为修改。

### P0：固定构建输入，建立性能与功能基线

- [x] 固定产品、内置内核、独立 Worker 的提交来源和工具链，记录 Hub、Worker 各自的完整模块清单。
- [x] 收敛到一个明确的构建入口；本地和 CI 共用参数约定。显式处理两级 `go.work`，验证 uTLS 实际来源。
- [x] 复用现有协议生成检查、版本检查、包内构建信息和校验清单，补足固定输入与组件组合信息。
- [x] 为 `dev-main`、分享分支起点、后续优化版本建立独立构建输出和测试数据目录，避免覆盖现有工作区配置。
- [x] 在兼容前提下使用相同 Worker、编译参数、窗口状态、网关数和流量负载；如不能一致，记录差异并分组比较。

### P1：修正分享和发现的按需启停

- [x] 将 `NewController`、发布器和发现协调器的资源启动移到显式运行阶段，并修正与实际行为不符的注释。
- [x] 分别定义分享、广播、浏览、导入连接的启动条件与停止条件，明确并发启动、重复停止和再次启动的行为。
- [x] 启动失败和取消时关闭已创建资源；停止时等待任务退出，禁止旧回调重建已经停止的实例。
- [x] 保持恢复用户已启用分享的行为；保留严格会话绑定、防火墙恢复和历史内网归属保护。
- [x] 更新现有 idle/lifecycle 测试，使其检查资源和任务生命周期；不把“允许固定数量后台循环”作为未使用零任务的证明。

验收：默认未启用时没有该功能的长期循环和监听；反复开关后任务、句柄、连接不持续增长；关闭发现不影响分享，关闭页面不影响使用中的连接。

回退：独立回退生命周期提交；配置格式保持兼容。

### P2：建立可选功能的契约和装配边界

- [x] 从服务实现提取轻量状态、错误、命令与事件类型；页面依赖客户端接口。
- [x] 将 relay 连接器和分享适配器从基础连接器工厂中分离，在装配入口显式注册；保持现有连接行为。
- [x] 对照 `Session`、`Source` 等现有接口提取必要能力，避免通用插件框架和无实际用途的抽象。
- [x] 为组件规定版本、能力、实例标识、请求标识、取消、超时、状态事件和有界消息规则。
- [x] 分离“组件不可用”“用户未启用”“业务正在运行”“业务失败”的状态，GUI 能准确呈现并允许恢复操作。

验收：标准核心包不依赖可选服务实现；可以用替代客户端测试页面和装配；缺失功能不会误用其他登录方式或扩大出口权限。

回退：保持配置和已有网络分享协议不变；按适配器、装配、页面依赖顺序回退。

### P3：接入清理分支，完成任务进程化

- [ ] 核对清理分支相对共同祖先的功能修改，列出可复用包、UI、配置及测试，再选择合并或移植；解决公共文件冲突后保留分享分支已有修复。
- [ ] 复用 `cmd/app-cleanup` 的现有操作与协议，扫描、备份查询、执行和恢复全部通过独立程序完成。
- [ ] 去掉组件缺失时的 GUI 进程内重操作回退，显示明确的不可用状态；提权仅用于需要特权的操作。
- [ ] 使用每任务唯一的计划和报告位置，限制文件访问；进度读取改为增量、有界展示，结束后释放详细扫描状态。
- [ ] 明确取消和崩溃恢复：清理任务不得在不可恢复的中间步骤直接强杀；备份与恢复日志按现有语义保留。

验收：清理组件缺失不影响 VPN；未使用时不运行清理进程；扫描、取消、提权拒绝、执行失败、恢复均有准确结果；完成后进程退出、GUI 大对象不长期保留。

### P4：归并内核补丁，统一依赖来源

- [ ] 对内置与独立内核建立补丁清单，区分协议兼容、网络栈调优、产品接入和上游已有修改；记录每项的来源及验证方法。
- [ ] 在 fork 的专用分支逐项归并，验证 Hub 使用的 aTrust 路径与 Worker 使用的 EasyConnect 路径；未覆盖的真实网关场景单独标注。
- [ ] 完成合并及验证后，将内置副本替换为固定子模块提交；保留原提交作为完整回退依据。
- [ ] 更新 Hub 依赖、Worker 构建根、patched uTLS 的依赖选择、IPC 生成器路径和 CI 检出方式。
- [ ] 将必要的工作区开发说明和 `tests/e2e` 纳入产品仓库，使新检出可按文档完成构建和验证。

### P5：将 relay 运行时迁入独立进程

- [ ] 增加 `cmd/app-relay`，产物使用 `core/connect-hub-relay.exe`（其他平台不带扩展名）。
- [ ] Hub 根据分享、浏览或导入连接任务启动组件，握手成功后调用；无有效任务后停止并等待退出。
- [ ] 复用 P2 的客户端边界与现有 LAN 分享协议，分别定义本机控制通道和流式数据通道；不把 `net.Conn` 或全部流量塞进控制 JSON。
- [ ] 通过授权适配器借用已有 VPN 会话，不额外登录网关；授权绑定会话代次和资源版本，关闭分享或会话失效即撤销。
- [ ] DNS 与拨号使用一致的会话归属；目标未知、资源撤销、会话离线和组件故障时均不得回退直接联网。
- [ ] 保留现有特权助手对防火墙及恢复日志的所有权；为正常退出、Hub 崩溃、relay 崩溃、版本不匹配分别设计处理。
- [ ] Hub 保存有界状态快照并在 UI 线程消费，拒绝旧实例事件；运行中的分享不随页面关闭而停止。

验收：未使用时没有 relay 进程；组件异常不结束基础 VPN；分享方与导入方都能完成业务、撤销和重连；完整进程树的内存、CPU、吞吐和延迟有前后对照。

回退：先停用独立 relay，恢复上一个已验证的组件实现及其配套构建；保留配置和离线保护，禁止混装后静默降级。

### P6：整理 GUI，形成有限的发行组合

- [ ] 先提取功能控制器，再迁移页面；逐步将根 `app` 的职责缩减到启动、装配和 UI 生命周期。

- [ ] 更新现状文档、开发说明、组件组合和验收记录，保留方案与已实施状态的区分。

验收：两个组合都能构建、启动、升级和退出；基础用户功能保持完整；UI 与组件缺失、混装、故障状态一致；核心包不包含可选服务依赖。

回退：发行组合和 GUI 迁移分别回退，保留数据兼容处理。

## 5. 测量与验证规则

### 5.1 资源场景

| 场景 | 观察目标 |
|---|---|
| 启动后从未使用可选功能 | 可选任务、监听、进程、固定代码与 UI 成本 |
| 打开页面但不启用服务 | 是否意外启动后台服务，轻量 UI 状态成本 |
| 启用分享、发现或清理 | 活跃工作所需的资源、延迟与吞吐 |
| 停止全部可选任务 | 进程退出、句柄关闭、任务结束及对象释放 |
| 连续开关至少 10 次 | 稳态资源是否随次数持续增长 |
| 最小化、恢复窗口 | 与现有 GC 和工作集修剪机制的关系 |
| 组件异常、VPN 重连、恢复旧配置 | 失败收敛、迟到事件、离线保护及恢复记录 |

Windows 同时记录各进程的 Private Bytes、Working Set、句柄、CPU，诊断构建记录 Go 堆和 goroutine；统计 Hub、全部 Worker、可选组件及相关助手。
共享系统服务单独列示，避免把其他用户或任务的资源误算为本次增量。
在相同窗口状态、预热时间和观测窗口下重复采样，报告稳态、峰值和波动；按需使用分配剖析定位增长来源。

P0 根据噪声和产品目标确定量化预算，在后续变更前写入基线记录。功能任务退出是明确门禁；内存不要求立即精确回到同一个数值，也不以强制工作集修剪代替生命周期修复。

### 5.2 每阶段验证

- 先运行受影响包和跨边界场景测试；阶段完成时运行 Hub、Worker、e2e 的相关完整检查及协议生成一致性检查。
- 生命周期改动覆盖取消、启动失败、重复停止、重新启动、迟到回调和崩溃；在具备工具链的平台运行相关竞态检查。
- 构建与打包改动验证 Windows/Linux 目标；涉及 macOS 的改动增加相应构建检查。构建成功不等于宿主网络行为验证通过。
- UAC、真实防火墙、Wintun、NRPT、跨机发现、网关认证等由真实环境验证，明确记录未测项，不能用 mock 或交叉编译替代。
- 文档变更只做路径、引用、结构和差异检查，不因纯文档更新重复运行网络或业务测试。

## 6. 提交与交付约定

1. 最初的方案交付已完成；当前按用户授权实施 P0–P3，P4–P6 保留为后续阶段。
2. 后续每阶段按“契约/实现 → 有意义的验证 → 文档状态”形成可独立回退的提交，不混入无关格式化。
3. 首轮实现范围为 P0、P1、P2、P3；在构建可复现、功能生命周期可验证之后推进内核归并和 relay 进程化。
4. P4 开始前另建 fork 工作分支并记录起点；产品分支提交固定 fork 指针，两个仓库分别维护历史。
5. 每阶段记录：实际变更、验证命令及环境、实测数据、剩余限制、对应提交和回退方式。只有验收完成才勾选本方案的任务。
6. 所有 P0–P6 阶段完成且通过回归后，再讨论合回 `dev-main`；标准版和扩展版从同一主线构建，不长期用功能分支代表发行版本。
